# EliteSQL Development Plan

Execution plan derived from [specs.md](specs.md). The phases follow the spec's roadmap, with acceptance criteria, a testing strategy and the architecture decisions already settled.

## Settled decisions

These questions were left open in the spec and are now resolved:

1. **Concurrency: a single process, multiple threads.** A lock file on open prevents a second process from opening the database. This covers web servers deployed as a single process with internal concurrency (Node, Go, Rust, Java, Python with threads or async): while one request writes, the others read and write in parallel via MVCC. Multi-worker deployments (gunicorn with several workers, PHP-FPM) do not open the file directly: they use the `elitesql serve` sidecar mode (Phase 4), a single process embedding the engine and exposing the same API over a Unix socket. Alternative without the sidecar: `gunicorn -w 1 --threads N` or single-worker async uvicorn. True multi-process (several processes opening the same file) stays out of V1; the manifest design must not preclude it later, but its cost is not paid now.
2. **Queries: a minimal SQL dialect starting in Phase 2.** Parser and executor for a strict subset (SELECT/INSERT/UPDATE/DELETE, simple WHERE, ORDER BY, LIMIT, INNER/LEFT/RIGHT JOIN). The schema is declared via DDL (`CREATE TABLE`) with the V1 types, which also settles the schema-declaration format.
3. **ANN: an existing crate behind our own interface.** HNSW via a mature crate (`hnsw_rs`, `usearch` or equivalent, to be evaluated in Phase 3) wrapped in our own `AnnIndex` trait. Persistence and rebuild use our own format, so swapping the crate later never changes the on-disk format.
4. **Primary key: auto-generated ULID text.** Every record gets a `text` ULID id generated by the engine when not provided. It matches the C API (`const char *id`), sorts by time, and is friendly to future sync.

## Workspace layout

Cargo workspace with crates split by responsibility:

```text
elitesql/
  crates/
    elitesql-core/      # storage, MVCC, WAL, manifest, recovery, indexes, compaction
    elitesql-sql/       # parser, heuristic planner, dialect executor
    elitesql-vector/    # AnnIndex trait, HNSW integration, persistence and rebuild
    elitesql-ffi/       # stable C ABI (cdylib + header)
    elitesql-cli/       # elitesql binary: check, repair, import/export, repl
  bindings/
    python/           # over the C ABI
    node/             # over the C ABI
  tests/
    crash/            # crash-injection harness
    fuzz/             # cargo-fuzz targets: WAL, manifest, parser
  benches/            # criterion + comparisons vs SQLite
```

Infrastructure from day one:

- CI: build + tests + clippy + fmt on every PR; short nightly fuzzing.
- `format_version` in the manifest from the first byte ever written to disk.
- Golden files of the on-disk format to catch compatibility breaks.

## Phases

Estimates assume one full-time developer and are indicative.

### Phase 0: Prototype (~3-4 weeks)

Goal: validate the append-only core and the API ergonomics before investing in durability.

Tasks:

- `elitesql-core` crate with a simple append-only format (self-contained directory).
- V1 types: `bool`, `int64`, `float64`, `text`, `blob`, `timestamp`, `json` (vector arrives in Phase 3).
- Insert/get/update/delete with per-record versioning and tombstones.
- ULID generation as the default PK.
- Per-version snapshot (logical reference, no GC yet).
- In-memory primary index rebuilt on open.
- Benchmark harness (criterion) against SQLite.

Acceptance criteria:

- Reads by id within 2x of SQLite; sequential inserts equal to or better than SQLite on the same hardware.
- Benchmarks reproducible with a single command.
- Explicitly NO crash-safety guarantees in this phase.

Status (2026-08-06): implemented in `crates/elitesql-core`. Tests green (12). Benchmarks on Apple Silicon: reads by id 1.39µs vs SQLite's 2.87µs (2x faster); sequential inserts with per-operation commit 248K/s vs SQLite autocommit's 59K/s (4.2x); SQLite in a single transaction (811K/s) still beats the per-operation mode, as expected until batch commits land in Phase 1. Extras already covered: CRC32 per entry and torn-tail discard on open.

### Phase 1: MVP Storage (~8-10 weeks)

Goal: the spec's fail-safe guarantees, complete and demonstrable.

Tasks:

- Durable WAL with per-entry checksum and idempotent replay.
- Atomic manifest + `manifest.prev`, published via atomic rename.
- Lock file for process exclusion.
- Real MVCC: every transaction reads from a stable snapshot.
- Optimistic commits with conflict validation (`CONFLICT_RETRY`).
- Secondary and unique indexes validated at commit.
- Crash recovery on open following the spec's sequence (manifest -> manifest.prev -> WAL replay -> rebuild of dirty indexes).
- Checksums on manifest, WAL and segment blocks.
- Durability modes `safe`, `balanced`, `fast`.
- Initial background compaction that respects referenced snapshots.
- Basic `elitesql_check` (validate checksums and references).
- Engine error catalog (the `elitesql_status` codes the FFI will expose).

Acceptance criteria:

- The crash-injection suite (see Testing) passes thousands of iterations: after a kill at any point, the DB opens to the last fully committed state.
- A commit is never partially visible, verified by property tests.
- Compaction never deletes data referenced by a live snapshot (dedicated test).
- WAL and manifest fuzzing with no panics and no invalid states accepted.

Status (2026-08-06): complete in `crates/elitesql-core`. Implemented: durable WAL with CRC and idempotent replay; atomic manifest + manifest.prev with safe healing; lock file (flock); MVCC with transactions (begin/commit/rollback), snapshots as guards that compaction respects, and optimistic commits with `Error::Conflict` (CONFLICT_RETRY); secondary and unique indexes validated at commit; safe/balanced/fast modes; memtable->segment checkpoint with WAL rotation; stop-the-world compaction; `check()`; error catalog with codes for the future FFI. Verification: 41 tests including real kill -9 crash injection (120 rounds run locally), corruption fuzzing (1000 seeds, no panics), a randomized model test with snapshots/reopen/compaction, and multi-record commit atomicity under a torn WAL. Benchmarks (Fast vs SQLite sync=OFF): reads 0.62µs vs 2.72µs (4.4x); per-operation inserts 187K/s vs 63K/s (3.0x); batch txn 311K/s vs SQLite's 841K/s.

Staging optimization (2026-08-07): removed the clones from the transaction path — schema cached per table in the Txn (previously the full TableSchema was cloned per insert), in-place normalize_record reusing the caller's map, in-place updates of staged records, and a commit with zero Record clones (payloads paired by reference, direct schema-ordered encode). Measured result: per-operation 187K/s -> 216K/s (+15%); batch unchanged (~307K/s) — profiling shows the batch is dominated by inherent per-record costs (ULID, BTreeMap staging, MVCC index apply under the write lock), not clones. Identified next levers (non-trivial, for a future performance pass): a per-commit payload arena (one Arc per commit referenced by offset instead of one Arc<Vec> per record) and table-grouped index apply (staged already iterates ordered by table; today we pay 2 catalog lookups and 2 String allocations per record under the write lock). Phase leftover: automatic background compaction (today it is explicit via `compact()`).

### Phase 2: Query Layer (~6-8 weeks)

Goal: the minimal, deliberately limited SQL dialect.

Tasks:

- Subset parser: evaluate a restricted `sqlparser-rs` vs a small hand-written parser; decide in the first week of the phase with a 2-3 day spike.
- DDL: `CREATE TABLE` with V1 types, regular and unique indexes.
- DML: `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
- `WHERE` with simple filters over indexed and non-indexed fields.
- Basic `ORDER BY` and `LIMIT`.
- `INNER JOIN`, `LEFT JOIN`; `RIGHT JOIN` normalized internally as a swapped `LEFT JOIN`.
- Minimal heuristic planner: use an index when one exists, full scan otherwise; push filters below the join when possible.
- Explicit, clearly worded rejection of everything outside the subset (FULL OUTER, subqueries, CTEs).

Acceptance criteria:

- An sqllogictest-style suite covering the whole subset, including cases that must fail with a clear error.
- Indexed joins over 1M-record datasets with reasonable latency, documented in benchmarks.
- The fuzzed parser produces no panics.

Status (2026-08-07): complete as the `sql` module inside `elitesql-core` (the separate `elitesql-sql` workspace crate is postponed until the FFI demands it). Spike decision: hand-written recursive-descent parser, not sqlparser-rs — the subset is small and closed, error messages stay ours ("not supported in V1" with an alternative), zero new dependencies, and an expression depth guard so fuzzing cannot blow the stack. Implemented: CREATE TABLE (strict V1 types with suggestions), CREATE [UNIQUE] INDEX, atomic multi-row INSERT returning ids, SELECT with WHERE (=, <>, <, <=, >, >=, AND/OR/NOT, IS NULL, IN), multi-column ORDER BY, LIMIT/OFFSET, aliases, chained INNER/LEFT/RIGHT JOIN (RIGHT = swapped LEFT), UPDATE/DELETE with affected counts and conflict retry. Heuristic planner: point lookup by id, indexed equality via find_eq, pre-join filter pushdown, index nested-loop when the probe side is small and the join column is indexed, hash join as fallback. Consistency: SELECT is read-committed; consistent snapshots via the Rust API. Verification: 19 sqllogictest-style tests + 4 fuzzing tests (6000 random/mutated inputs without panics, deep nesting cut off by the guard). Benchmarks over 1M orders + 10K users: point lookup via unique index 3.9µs (full SQL path), indexed join with ORDER BY+LIMIT 361µs, unindexed full scan 1.1s (the spec's known limit). User documentation in manual.md.

### Phase 2.5: Basic aggregates and date/time types (~2-3 weeks)

Added on 2026-08-07: aggregates were referenced in manual.md as "Phase 2.x" without a real phase assigned, and date/time were promoted from V1.1-optional to required by product decision.

Tasks:

- `date` type: days since Unix epoch (logical i32). SQL literal 'YYYY-MM-DD' coerced by column type; real-date validation.
- `time` type: microseconds since midnight (i64). SQL literal 'HH:MM:SS[.ffffff]'; range validation.
- Both comparable, sortable and indexable like any scalar.
- Global aggregates: COUNT(*), COUNT(col), SUM, AVG, MIN, MAX.
- GROUP BY over one or several columns (hash aggregation in the executor).
- HAVING with simple predicates over the SELECT's aggregates.
- Composition with the existing subset: WHERE before grouping, ORDER BY over output columns, LIMIT; clear rejection of nested aggregates, DISTINCT inside aggregates and expressions.

Acceptance criteria:

- An sqllogictest-style suite for aggregates including NULL semantics (COUNT(col) ignores NULL, SUM/AVG of an empty set is NULL, MIN/MAX ignore NULL).
- Full date/time roundtrip: Rust API + SQL + secondary indexes + ORDER BY; invalid literals ('2026-02-30', '25:00:00') rejected with a clear error.
- Parser fuzzing extended to the new productions with no panics.

Status (2026-08-07): complete. Types: `date` (days since epoch, our own civil-calendar algorithm with real validation including leap years — 2100-02-29 is rejected) and `time` (microseconds since midnight with optional .ffffff fraction); string literals coerced by column type in INSERT/UPDATE/WHERE (also against indexes), public constructors Value::parse_date/parse_time/date_from_ymd/time_from_hms_micro; comparable, sortable, indexable and groupable. Aggregates: COUNT(*)/COUNT(col)/SUM/AVG/MIN/MAX with hash aggregation in first-seen order, multi-column GROUP BY (NULLs group together), HAVING over grouped columns and aggregates (even aggregates absent from the SELECT), ORDER BY by output name or alias, and composition with WHERE/joins/LIMIT/OFFSET. Standard NULL semantics; int64 SUM with overflow detection (an error, not a wrap) and float64 promotion on mixes. Clear rejections: aggregates in WHERE (points at HAVING), ungrouped column in SELECT, COUNT(DISTINCT), SUM(*), SUM/AVG over non-numeric columns, ORDER BY with an aggregate call (asks for an alias). Verification: 11 aggregate tests + 8 date/time/timestamp tests + fuzz extended to the new productions; 99 tests in total, clippy clean.

Datetime addendum (2026-08-07): instead of a separate `datetime` type (timestamp already is the instant type; two instant types confuse), `timestamp` accepts string literals 'YYYY-MM-DD HH:MM:SS[.ffffff]' interpreted as naive UTC — space or T separator, optional Z suffix, and date-only as midnight — in INSERT/UPDATE/WHERE and against indexes, with Value::parse_timestamp in the API. Timezone offsets rejected on purpose: the engine stores instants; timezone presentation belongs to the application.

### Phase 3: Vector Native (~5-6 weeks)

Goal: vectors as a first-class type and index.

Tasks:

- `vector<float32, N>` type with dimension validation on insert/update.
- Our own `AnnIndex` trait; a 1-week spike evaluating `hnsw_rs` vs `usearch` (recall quality, memory, license, maintenance) with the decision documented.
- Our own index persistence: checksummed metadata, graph rebuildable from canonical data if marked corrupt.
- `search_vector` with `top_k`, `metric` (cosine, dot, l2), `ef_search` and a metadata filter.
- Indexing modes `sync` (searchable at commit) and `async` (enters in background).
- Tombstone/update handling in the ANN index (logical deletion + rebuild at compaction).

Acceptance criteria:

- recall@k benchmarks against ground truth on public datasets (e.g. SIFT1M or a subset).
- Full index rebuild from canonical segments works and is covered by tests.
- A crash during async indexing never corrupts canonical data (crash injection extended to this phase).

Status (2026-08-07): complete. Spike outcome (documented pivot): hnsw_rs 0.3.4 was evaluated and failed the recall criterion — its upper-layer descent takes a single greedy step per layer instead of iterating to the local minimum (search_filter in its hnsw.rs), measuring recall@10 of 0.47-0.77 at ef=128 and non-monotonic in ef; usearch was rejected for its C++ toolchain (it compromises the WASM target). Final decision: our own HNSW (~300 lines, Malkov & Yashunin with the neighbor-selection heuristic), which also serves the long-term vision (full control for future persistence and MVCC integration). Implemented: vector<float32,N> type (Value::Vector, Column::vector(dim), dimension validation on insert/update, vector(N) in CREATE TABLE and JSON-array literal in SQL INSERT); create_vector_index with cosine/dot/l2 metrics and m/ef_construction parameters; search_vector with top_k, ef_search, metadata equality filter and escalating over-fetch; sync mode (searchable at commit) and async mode (background thread with an observable backlog and wait_vector_indexing); logical deletion with tombstones filtered at search time and physical rebuild at compaction; index rebuilt from canonical data on open (the graph is disposable by design). Verification: 12 vector tests (recall >= 0.9 vs brute force on 2K vectors, filters, update/delete, reopen, compaction, metrics, async) + dedicated crash injection (kill -9 during async indexing: canonical data and vector payloads intact, rebuilt index usable). Benchmark on 100K clustered dim-64 vectors with in-process brute-force ground truth: recall@10 0.88 (ef=128) and 0.97 (ef=256), search 95µs (ef=64) to 156µs (ef=128). Note: a real SIFT1M run is pending a dataset download; the harness already measures recall against exact ground truth.

Graph persistence (2026-08-07): implemented. The full HNSW graph is serialized into vectors/ (ESQLVIDX magic, body CRC32, index identity and dump commit version) on database close and at compaction, with atomic writes (tmp + rename + fsync). On open: if the dump validates and its version is <= the committed version, it is loaded and incrementally caught up with everything committed after the dump (changed/deleted records and entries compaction left behind); if it is corrupt, the definition changed, or the dump comes "from the future" (a manifest.prev rollback), it is rebuilt from canonical data without error — the graph stays disposable. Loading validates structural invariants (entry point, neighbors in range and at or below their layer) so a corrupt file can never cause a panic. Result: opening 100K vectors goes from a full rebuild to ~134ms. Tests: identical loads after clean close, catch-up with a stale dump (later inserts/updates/deletes reflected), corruption with fallback to rebuild, and a refreshed, shrunken dump after compaction.

### Phase 4: Developer Experience (~8-10 weeks)

Goal: make EliteSQL usable outside Rust.

Tasks:

- `elitesql-ffi`: stable C ABI per the spec, header, semantic ABI versioning.
- Python binding over the C ABI, published as a wheel. Requirement: release the GIL during every engine call, so a single-process threaded deployment truly parallelizes DB operations.
- Node binding over the C ABI (napi), published on npm.
- `elitesql` CLI: query repl, `check`, `repair`, import/export (JSON and CSV).
- `elitesql serve <db>` sidecar mode: a single process embedding the engine exposes the full API over a Unix socket, for multi-worker deployments (gunicorn, PHP-FPM). Bindings connect transparently (socket detection or connection string) without changing the user's API. The engine does not change: the single-process guarantees are preserved and concurrent clients benefit from the internal parallel writers.
- `elitesql_repair`: recover valid records, always report what was discarded, never repair silently.
- Automatic read-only mode on unrecoverable corruption.
- Docs: getting started, SQL dialect reference, recovery guide, on-disk format.
- Reproducible benchmarks published with the repo.

Acceptance criteria:

- A user can run the full flow (create, insert, query, search_vector, snapshot) from Python and Node without touching Rust.
- Reproducible demo: gunicorn with 4 workers against `elitesql serve`, concurrent visitors reading and writing without blocking each other.
- `elitesql check` detects the corruptions injected by the crash-test suite.
- Docs sufficient for onboarding without reading the code.

Status (2026-08-07): phase core complete. Delivered:
- C ABI (`crates/elitesql-ffi`, libelitesql cdylib+staticlib, header include/elitesql.h): open/close/query(SQL)/search_vector/create_vector_index/checkpoint/compact/check/repair. Stable status codes (Error::code), messages via thread-local elitesql_last_error, panic-safe (catch_unwind — never unwinds across the ABI). JSON payloads with tagged values ({"$t": date|time|timestamp|blob|json|vector}) via the shared elitesql_core::jsonio module.
- `elitesql` CLI (crates/elitesql-cli): query, repl, tables, check, compact, repair, JSONL export/import with per-column-type coercion, serve, version. No argument-parsing dependencies.
- `elitesql repair`: salvage into a fresh DB from segments+WAL, corruption-tolerant (valid prefix per file), never silent — reports recovered/deleted/skipped with a note per damage found.
- `elitesql serve <db> <socket>` sidecar: Unix socket, line-delimited JSON protocol (query, search_vector, create_vector_index, checkpoint, compact, ping), one thread per connection over a shared Db.
- Python binding (bindings/python/elitesql.py): embedded EliteSQL over the C ABI via ctypes — the GIL is released automatically on every foreign call, meeting the phase requirement — plus SidecarClient for multi-worker; decodes date/time/timestamp into datetime.*, blob into bytes, and exposes check()/repair().
- Node binding (bindings/node/elitesql.js): pure-JS sidecar client with zero dependencies, promise API, decodes into Date/Buffer.
- Acceptance demo passed: examples/gunicorn_demo/run_demo.sh — real gunicorn with 4 workers against elitesql serve; 8 visitors x 25 concurrent requests: 200/200 writes recorded, 4 distinct worker PIDs, 0.7s wall, worst request 41ms, zero blocking.
- Verification: 105 Rust tests + full CLI e2e + Python FFI smoke (full flow incl. vectors and filters) + Node sidecar e2e.

Phase closure (2026-08-07): leftovers completed.
- Snapshots in the ABI: elitesql_snapshot_open/close/get/scan + a Snapshot class in Python (context manager) — stable reads from bindings.
- Read-only mode: DbOptions.read_only / Db::open_read_only / {"read_only":true} ABI option / --read-only in the CLI. Shared lock (several RO readers coexist), tolerant loading (valid prefix of damaged files instead of refusing), zero disk writes (verified byte-for-byte in a test), every write returns ReadOnly (code 13). It is the step before repair when inspecting a damaged database.
- Packaging: pyproject.toml (wheel buildable with python -m build) and package.json + elitesql.d.ts for the Node client. Publishing to PyPI/npm is an external step for when the project goes public.
- Onboarding docs: docs/getting-started.md, docs/recovery.md, docs/disk-format.md.
- Decision recorded: the native embedded Node binding (napi) is deferred — the Node path is the sidecar (zero dependencies, no build toolchain on npm install); napi will be justified if a single-process Node use case needs embedded latencies.

### Phase 5: Advanced (unestimated; prioritize on arrival)

- Basic full-text and `search_hybrid`.
- Blob chunking with per-chunk checksums.
- Quantized vectors (`vector<int8, N>`, IVF/PQ).
- WASM target.
- Optional local-first sync.
- Explore single-file mode.

Status (2026-08-07): prioritization executed — the phase asked to "prioritize on arrival" and the priority was the AI-native promise. Implemented and tested:
- Basic full-text: in-memory inverted index with BM25 ranking (k1=1.2, b=0.75) over text columns; a deliberately predictable tokenizer (Unicode alphanumeric runs, lowercase, 2..64 chars, no stemming, no stopwords). create_text_index + search_text with a metadata filter; maintained at commit, rebuilt on open and compaction, definition persisted in the catalog. Exposed in the ABI, sidecar, Python and Node.
- search_hybrid: Reciprocal Rank Fusion (k=60) of BM25 + ANN, one or both modalities, with a shared filter. A document present in both rankings wins — verified in tests.
- Quantized vectors: a quantized option on the ANN index — int8 with a per-vector scale (x ~ q*scale), integer distances (i64 dot) or on-the-fly dequantization, ~4x less memory and dump (verified by file size), recall >= 0.8 vs brute force in tests. vidx format v3; old dumps are discarded and rebuilt.
- Blob chunking: blob values >= external_blob_threshold (default 256 KiB) go out-of-line to blobs/<ulid>.blob with an ESQLBLOB header + CRC + length, written and fsynced BEFORE the WAL commit that references them; the payload stores a reference (tag 11) resolved and validated on read. GC at compaction (deletes unreferenced chunks, including orphans from torn commits); check() validates chunks referenced from segments and WAL; salvage resolves them or reports. Out of the transactional critical path, as the spec demanded.
- Verification: 9 dedicated tests (BM25 ranking, text-index updates/deletes/reopen/compaction, RRF, quantized recall + dump size, blob roundtrip + GC + detected corruption, read-only on a healthy and on a corrupt database) + Python and Node e2e smokes.

Deferred with a decision (deliberately not implemented):
- WASM target: the core uses fs/flock/threads/Instant; porting it requires a platform-abstraction layer — a project of its own, justified when a concrete browser/edge consumer exists.
- Local-first sync: "optional" in the spec; requires protocol design (CRDTs or log shipping) deserving its own spec.
- IVF/PQ: int8 scalar quantization covers the memory goal at the current data scale; IVF/PQ when datasets exceed ~10M vectors.
- Single-file mode: the self-contained directory remains simpler for compaction and indexes; re-evaluate on real demand.

Post-closure addition (2026-08-07): backup and restore. `Db::backup(dst)` is a snapshot-consistent logical copy into a fresh directory — concurrent writers are never blocked, ids/schemas/index definitions are preserved, the copy is born compacted, written to `<dst>.partial` and renamed only after the final checkpoint (an interrupted backup never leaves a half-written directory under the final name). `restore(src, dst)` refuses an existing destination, runs `check` on the backup (a damaged backup is reported, never restored), copies the canonical files and opens the result once to replay the WAL and rebuild derived indexes. Both exposed in the CLI (`elitesql backup` verifies the copy with `check` before reporting success). 5 dedicated tests including a hot backup under 4 concurrent writer threads and a corrupted-backup refusal. Not yet in the ABI/sidecar/bindings — pending demand, same criterion as napi.

## Testing strategy (cross-cutting)

Durability testing is first-class work, not an afterthought. It is built in Phase 1 and maintained across every phase:

- **Crash injection**: a harness that runs workloads while killing the process at random points (including between write and fsync, and mid-manifest-rename), then reopens and verifies invariants. Runs in CI with a short budget and nightly with a long one.
- **Property tests** (proptest): MVCC invariants (a reader never sees intermediate state), WAL replay idempotence, update-then-read semantic equivalence.
- **Fuzzing** (cargo-fuzz): corrupt WAL, corrupt manifest, malformed SQL statements. Never panic, never accept invalid state.
- **Concurrency tests**: many readers + multiple concurrent writers with commit-serializability verification.
- **Golden files**: binary fixtures of the on-disk format per version; changing the format requires an explicit `format_version` bump.

## Main risks

- **SQL from the start grows Phase 2.** Mitigation: a strict, immovable subset during V1, and an early sqlparser-rs spike to avoid writing a parser from scratch unless needed.
- **HNSW crate integration with MVCC/tombstones.** ANN crates rarely support deletion well. Mitigation: our own trait, logical deletion and rebuild at compaction; the on-disk format is ours.
- **mmap + crash safety** has dark corners (dirty pages, msync). Mitigation: mmap for reads only; every write goes through write + explicit fsync.
- **V1 scope.** Every new feature must justify its weight (spec principle); anything outside the V1 scope is rejected by default.

## Remaining open questions

Decide no later than the start of the phase that needs them:

- **Nullability** (Phase 0): proposal — fields nullable by default, `NOT NULL` opt-in in the DDL.
- **Exact `json` semantics** (Phase 2): whether internal paths can be filtered in V1 or it is store/read only.
- **Snapshot retention policy** (Phase 1): how many live snapshots and how they are released (explicit API vs TTL).
- **Lock file name and format** and behavior with zombie processes (Phase 1).
- **Sidecar protocol** (Phase 4): proposal — a minimal versioned binary protocol over a Unix socket; avoid heavy dependencies like gRPC.
