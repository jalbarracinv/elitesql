# Propuesta: perfil de compatibilidad relacional para EliteSQL

**Estado:** implementado y cubierto por pruebas de integración  
**Motivación:** permitir portar aplicaciones web relacionales pequeñas, como un
servicio de firma documental, sin convertir EliteSQL en un clon de MySQL ni
renunciar a sus garantías de WAL, MVCC y proceso propietario único.

La implementación conserva compatibilidad de lectura con catálogos anteriores
mediante campos opcionales con valores predeterminados: no fue necesario
invalidar el formato existente. El high-water de identity sí se persiste en
WAL y manifest y se reconstruye al abrir bases previas.

## Decisión central

EliteSQL **no cambiará** su clave física implícita `id text` ni dejará de
generar ULID. Es una propiedad importante del formato, de las referencias
internas y de la concurrencia del motor. En su lugar, añadirá columnas de
identidad enteras, que son columnas de aplicación con un contador persistente
y transaccional:

```sql
CREATE TABLE documents (
  document_id int AUTO_INCREMENT,
  owner_id    int NOT NULL,
  title       varchar(255) NOT NULL,
  status      enum('draft', 'sent', 'completed') NOT NULL DEFAULT 'draft',
  created_at  timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

El registro tendrá, por tanto, dos identificadores:

| Campo | Tipo | Uso |
|---|---|---|
| `id` | `text` (ULID implícito) | identidad física, API nativa de EliteSQL y nuevas integraciones |
| `document_id` | `int` identity | compatibilidad con URLs, relaciones y APIs existentes que esperan enteros |

Esta separación permite migrar una aplicación gradualmente: las relaciones
actuales pueden conservar sus `*_id int`, mientras que un producto nuevo puede
usar directamente los ULID. Nunca se debe permitir que `id` sea entero o que
un `UPDATE` cambie cualquiera de las dos identidades.

## Objetivo y límites

El perfil cubre el subconjunto que más bloquea la migración de una aplicación
transaccional convencional:

1. IDs enteros autogenerados y recuperación inequívoca del valor generado.
2. Integridad referencial de una columna y borrado en cascada atómico.
3. Transacciones multi-sentencia accesibles desde Python y mediante sidecar.
4. Operaciones atómicas habituales: incremento/decremento condicional,
   `CURRENT_TIMESTAMP`, inserción idempotente por unicidad y
   `COUNT(DISTINCT ...)`.
5. Adaptación DB-API suficiente para código que espera cursor, filas y
   `lastrowid`.

No se propone implementar sintaxis MySQL completa, un optimizador compatible
con MySQL, triggers, procedimientos, bloqueos pesimistas, ni transacciones
distribuidas. Consultas con CTE, subconsultas, ventanas o funciones arbitrarias
seguirán fuera de alcance.

## Fase 1 — Identidades enteras seguras

### Superficie SQL

Se aceptarán estas dos grafías equivalentes al crear una tabla:

```sql
order_no int GENERATED BY DEFAULT AS IDENTITY
order_no int AUTO_INCREMENT
```

`AUTO_INCREMENT` es la forma de compatibilidad MySQL; el catálogo guardará la
forma canónica `identity`. Reglas:

- Sólo vale para una columna `int`, no anulable y única. `CREATE TABLE` crea
  automáticamente el índice único si no se declara uno equivalente.
- Una tabla puede tener, como máximo, una columna identity.
- `BY DEFAULT` permite suministrar el valor explícitamente durante importación
  o migración; una inserción explícita avanza el contador si el valor es mayor.
- La primera cifra es `1`, salvo `START WITH n` si se añade posteriormente.
- El rango es `1..=i64::MAX`; el desbordamiento falla antes de publicar el
  commit.
- Los números son únicos y crecientes, pero **no contiguos**. Abortos,
  conflictos reintentados y fallos pueden dejar huecos. Es la semántica segura
  y familiar de `AUTO_INCREMENT`, no un contador de negocio.

Se añadirá `INSERT ... RETURNING` para devolver columnas ya materializadas:

```sql
INSERT INTO documents (owner_id, title)
VALUES (%s, %s)
RETURNING document_id, id, created_at;
```

Para no romper la forma de respuesta actual, un `INSERT` sin `RETURNING`
seguirá devolviendo `{"inserted":["<ulid>"]}`. Con `RETURNING` devolverá el
resultado de filas normal. El cursor DB-API expondrá como `lastrowid` el primer
valor identity generado por ese `INSERT`; para una inserción múltiple se
documentará que es el primero, como MySQL. Código nuevo debe consumir
`RETURNING`, que es inequívoco y también funciona para ULID.

### Persistencia y concurrencia

El contador no puede ser un `MAX(col)+1`, ni una actualización de
`catalog.json` por inserción. Ambas alternativas son lentas y permiten carreras
o reutilización tras recuperación.

Se añadirá al estado durable de cada tabla un `identity_high_water`:

- `Txn::insert` reserva valores desde un contador atómico por tabla y los
  coloca en el registro staged; así una segunda operación del mismo `Txn` puede
  usar el entero antes del `commit`.
- El commit que publica un valor lleva el high-water correspondiente en la
  entrada WAL, junto con los registros. Recuperación aplica ambos de forma
  idempotente antes de hacer visible el commit.
- Si un proceso muere tras reservar pero antes de publicar, el valor puede
  reutilizarse al reiniciar; nunca llegó a ser visible ni fue confirmado. Si
  fue publicado, recovery no lo reutiliza.
- Al abrir una base antigua o importar IDs explícitos, el motor inicializa o
  corrige el high-water al máximo identity visible. La verificación (`check`)
  comprueba que ningún registro identity lo supera.

El contador es parte del estado transaccional y del formato. Por ello requiere
subir la versión del catálogo/formato, escribir un migrador de formato y hacer
que una versión antigua rechace la base claramente, en vez de abrirla de forma
parcial.

### Trabajo técnico

1. Extender `Column`/`TableSchema` con `identity: Option<IdentityDef>` y el
   estado durable de secuencia por tabla.
2. Extender lexer, AST y parser para `AUTO_INCREMENT`, la forma canónica
   `GENERATED ... IDENTITY`, `RETURNING` y `DEFAULT` como valor de INSERT.
3. Reservar y validar identities en `Txn`, en inserciones autocommit y en la
   ruta SQL; incluirlas en WAL, manifest/recovery, backup, restore, import,
   export, compactación y reparación.
4. Añadir una proyección `RETURNING` limitada a columnas del registro insertado;
   no mezclarla con `UPDATE`/`DELETE` en esta fase.

## Fase 2 — Integridad referencial acotada

Se añadirá una clave foránea de una columna, inicialmente sólo en `CREATE
TABLE`:

```sql
CREATE TABLE document_signers (
  document_id int NOT NULL REFERENCES documents(document_id) ON DELETE CASCADE,
  user_id     int NOT NULL REFERENCES users(user_id) ON DELETE RESTRICT,
  role        text NOT NULL
);
```

Una clave foránea puede apuntar a `id` o a una columna con índice único. Las
dos columnas deben tener el mismo tipo. La columna local recibirá un índice no
único automáticamente, porque validar un padre o recorrer hijos no puede
degradar a un escaneo completo sin aviso.

Semántica propuesta:

- `RESTRICT` es el valor predeterminado y rechaza el borrado de un padre si
  quedan hijos.
- `CASCADE` expande los borrados de hijos dentro del mismo `Txn`. El WAL sólo
  publica padre e hijos juntos; tras un crash se ve todo o nada.
- `SET NULL` se puede añadir junto con `CASCADE` si el caso de uso lo exige;
  no es requisito inicial.
- Validación y expansión se hacen contra la vista staged del `Txn`, por lo que
  `INSERT parent`, `INSERT child` y `DELETE parent` en la misma transacción son
  correctos aunque estén en órdenes no triviales.
- Se detectan ciclos y una cascada con demasiados registros falla antes de
  publicar, con límites configurables de profundidad y operaciones.

No se propone `ON UPDATE CASCADE`: la identidad implícita no cambia y los IDs
identity deberían tratarse como inmutables. Cambiar una clave de negocio se
hará mediante una migración explícita.

Esto exige añadir `ForeignKeyDef` al catálogo y extender la validación de
unicidad/índices durante el commit. `DROP TABLE`, `DROP COLUMN` y `DROP INDEX`
deben rechazar una operación que dejaría una referencia rota. Las alteraciones
de FKs (`ALTER TABLE ... ADD/DROP CONSTRAINT`) quedan para una fase posterior;
el migrador puede crear las tablas vacías con las relaciones ya declaradas.

## Fase 3 — Transacciones en bindings y sidecar

El núcleo Rust ya posee `Txn`, pero la aplicación Python y el sidecar no pueden
hoy usarlo como unidad de trabajo. Esta fase expone la misma semántica, no una
implementación alternativa.

### API

La FFI añadirá un handle opaco `elitesql_txn`; Python expondrá:

```python
with db.transaction(retries=3) as tx:
    doc = tx.execute(
        "INSERT INTO documents (owner_id, title) VALUES (%s, %s) "
        "RETURNING document_id",
        [user_id, title],
    ).fetchone()
    tx.execute(
        "UPDATE users SET credits = credits - %s "
        "WHERE user_id = %s AND credits >= %s",
        [cost, user_id, cost],
    )
```

El sidecar mantendrá el `Txn` asociado a una conexión, con comandos de
protocolo `begin`, `query_in_txn`, `commit` y `rollback`. `BEGIN`/`COMMIT` SQL
se aceptarán sólo en las conexiones de binding/sidecar como azúcar equivalente,
no en la API SQL stateless del CLI.

Límites obligatorios: un `Txn` de sidecar tendrá tamaño máximo, plazo máximo y
una conexión no podrá empezar uno anidado. Si se corta la conexión, el servidor
hace rollback. `COMMIT` puede devolver `CONFLICT_RETRY`; el wrapper Python
reintentará el bloque completo sólo si es declarado reejecutable. Nunca se
reintenta automáticamente un bloque que haya enviado correo, firmado fuera de
la base u ocasionado otro efecto externo.

Para que SQL opere contra una transacción se extraerá el ejecutor actual detrás
de una interfaz de lectura/escritura compartida por `Db` y `Txn`. No se deben
ensamblar varias sentencias como texto ni simular atomicidad desde Python.

## Fase 4 — Expresiones y compatibilidad DML mínima

Esta fase se limita a formas que mejoran corrección, no a un lenguaje de
funciones general.

| Forma | Semántica propuesta | Motivo |
|---|---|---|
| `SET c = c + expr`, `c - expr`, `c * expr`, `c / expr` | expresiones tipadas sólo en `UPDATE SET`; overflow/división por cero son errores | actualizaciones atómicas de saldo, contadores y cuotas |
| `CURRENT_TIMESTAMP` / `NOW()` | una marca UTC por sentencia; también válida como `DEFAULT CURRENT_TIMESTAMP` | auditoría y creación de documentos |
| `INSERT ... ON CONFLICT DO NOTHING` | ignora únicamente una violación de índice único | idempotencia segura |
| `INSERT IGNORE` | alias de la forma anterior, no suprime errores de tipo, NOT NULL o FK | compatibilidad sin ocultar corrupción |
| `COUNT(DISTINCT col)` | deduplicación con spill y el mismo presupuesto de memoria de `GROUP BY` | métricas de dashboard |
| `CASE WHEN ... THEN ... ELSE ... END` | pospuesto salvo que las consultas reales lo requieran; el dashboard puede calcularlo en aplicación | evitar convertir el AST en SQL general |

Una actualización como la siguiente será una única operación atómica y ya
tendrá reintento optimista interno:

```sql
UPDATE users
SET credits = credits - %s
WHERE user_id = %s AND credits >= %s;
```

La aplicación debe comprobar `affected = 1` antes de crear el documento. Si
ambas acciones forman una unidad de negocio, van dentro del `Txn` de la fase 3.

## Fase 5 — Tipos y adaptador de aplicación

Son mejoras de bajo riesgo, separadas de la semántica transaccional:

- `varchar(n)` se guarda como `text` pero conserva el máximo en el catálogo y
  valida longitud Unicode al escribir. `varchar` sin longitud equivale a
  `text`.
- `longtext` es alias de `text`.
- `enum('a', 'b')` es `text` con conjunto permitido persistido y validado por
  el motor; no se usa una tabla implícita.
- `PRIMARY KEY` sobre `id` se acepta como declaración redundante. Sobre una
  identity, se traduce a su índice único. No se admiten claves primarias
  compuestas.
- La capa Python `Connection`/`Cursor` implementa `cursor()`, `execute()`,
  `executemany()`, `fetchone()`, `fetchall()`, `rowcount` y `lastrowid`, sobre
  la respuesta tipada actual. `query()` continúa disponible y no cambia.

El adaptador no pretende aceptar SQL producido por cualquier ORM. Su valor es
reducir cambios en aplicaciones DB-API sencillas y hacer explícitos los puntos
que aún requieren una migración de consulta.

## Orden de entrega y criterios de aceptación

1. **Identity + RETURNING.** Pruebas de 100 escritores concurrentes, rollback,
   conflicto, reapertura, crash entre WAL/manifest, importación de IDs
   explícitos, backup/restore y formato anterior. Un mismo número no puede
   aparecer en dos registros visibles.
2. **Txn en FFI/sidecar.** Prueba de Gunicorn con cuatro workers que ejecuta
   miles de "descontar crédito + crear documento" y comprueba que no hay ni
   documentos no cobrados ni créditos negativos. Desconexión y timeout hacen
   rollback.
3. **FK/cascade.** Pruebas de padre/hijo staged, `RESTRICT`, cadenas y ciclos
   de cascada, recuperación después de kill -9 y restauración de backup.
4. **DML mínimo.** Pruebas de límites de `int64`, timestamp estable,
   `DO NOTHING` que no oculta un error de esquema/FK y `COUNT(DISTINCT)` que
   derrama a disco con memoria acotada.
5. **Adaptador Python.** Pruebas de compatibilidad con las rutas de creación,
   firma, auditoría y dashboard de la aplicación objetivo, tanto embedded de
   proceso único como sidecar Unix.

La conversión MySQL a EliteSQL sólo debe iniciar después de completar los dos
primeros hitos. El migrador creará las identities con valores explícitos,
validará relaciones y unicidad, ajustará los high-water y comparará conteos y
hashes por tabla antes del corte.

## Riesgos y decisiones explícitas

- Las identidades enteras solucionan compatibilidad; no deben usarse como
  orden exacto de commits ni como mecanismo de seguridad. Para nuevos enlaces
  públicos se prefiere el ULID.
- Las FKs elevan la complejidad de escritura y compactación. Se mantienen de
  una columna y con índices obligatorios hasta tener evidencia de que hace
  falta más.
- Las transacciones remotas retienen memoria y snapshot, por lo que los límites
  de tiempo/tamaño no son opcionales.
- `INSERT IGNORE` de MySQL tiene semántica demasiado amplia. EliteSQL sólo
  ignorará conflictos de unicidad explícitamente; los demás errores deben
  seguir siendo visibles.
- Esta propuesta vuelve viable la adaptación de la aplicación de firma, pero
  no elimina el riesgo de usar un motor alfa en producción. La migración debe
  seguir una ejecución paralela, backups verificables y un plan de reversión.
